# Data model

Logical schema for the Support Ticket Management System. PostgreSQL is the primary database. Types and constraints below are chosen so the same Flyway scripts can run on H2 for local use.

Scope is only **tickets** and **comments**. No users, auth, audit, notifications, or soft delete.

Status transition rules live in the **service layer**, not in the database (except a CHECK on allowed status *values*).

## 1. Overview

```text
tickets (1) ──────< (N) comments
```

- One ticket has many comments.
- A comment belongs to exactly one ticket.
- Ticket delete is out of scope; the foreign key still prevents orphan comments.

**IDs:** `BIGINT`, generated by the database (`GENERATED BY DEFAULT AS IDENTITY`). Matches the architecture assumption of server-generated `Long` ids. Do not use UUID.

## 2. `tickets`

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `id` | `BIGINT` | NO | identity | Primary key |
| `title` | `VARCHAR(255)` | NO | — | Required, not blank (blank also rejected by the app) |
| `description` | `VARCHAR(4000)` | NO | — | Required, not blank |
| `status` | `VARCHAR(32)` | NO | `'OPEN'` | See status values below |
| `priority` | `VARCHAR(32)` | NO | — | See priority values below |
| `assignee` | `VARCHAR(255)` | YES | `NULL` | Optional free text; `NULL` means unassigned |
| `created_at` | `TIMESTAMP` | NO | `CURRENT_TIMESTAMP` | Set on insert; never updated |
| `updated_at` | `TIMESTAMP` | NO | `CURRENT_TIMESTAMP` | Set on insert; app updates on every ticket change |

**Primary key:** `id`

**Required:** `title`, `description`, `status`, `priority`, `created_at`, `updated_at`  
**Nullable:** `assignee` only

`assignee` as free text is an implementation assumption from `spec/requirements.md`. Clearing the assignee stores `NULL`.

## 3. `comments`

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `id` | `BIGINT` | NO | identity | Primary key |
| `ticket_id` | `BIGINT` | NO | — | FK → `tickets.id` |
| `body` | `VARCHAR(4000)` | NO | — | Comment text; required, not blank |
| `created_at` | `TIMESTAMP` | NO | `CURRENT_TIMESTAMP` | Set on insert; comments are not edited |

**Primary key:** `id`

No author column (no login). Comments are not updated or deleted in this assignment.

## 4. Priority and status

Stored as **uppercase strings**, same names as the Java enums. Not a separate lookup table.

**Status (required):** `OPEN`, `IN_PROGRESS`, `RESOLVED`, `CLOSED`, `CANCELLED`

- Database default on insert: `'OPEN'`
- The application also sets `OPEN` on create and does not accept a client status
- CHECK constraint: value must be one of the five strings
- Allowed *transitions* are not encoded in SQL

**Priority (required):** `LOW`, `MEDIUM`, `HIGH`

- No database default; the client must send a valid value
- CHECK constraint: value must be one of the three strings
- These three values are an assumption from `spec/requirements.md`

Use `VARCHAR` plus `CHECK`, not PostgreSQL `ENUM` types (poor H2 portability and awkward to change).

## 5. Relationship, foreign keys, constraints

- **FK:** `comments.ticket_id` → `tickets.id`
- **On delete / update:** `NO ACTION` (do not cascade). Ticket delete is not a feature; this avoids accidental comment wipes.
- **CHECK** on `tickets.status` and `tickets.priority` as above
- **CHECK** that `title`, `description`, and `comments.body` are not empty after trim is optional in SQL; the backend already validates this. Prefer app validation over `TRIM` checks for H2/Postgres sameness.
- No unique constraint on title (duplicate titles are allowed)

## 6. Indexes

| Index | Table | Columns | Why |
| --- | --- | --- | --- |
| `pk_tickets` | `tickets` | `id` | Primary key |
| `pk_comments` | `comments` | `id` | Primary key |
| `idx_tickets_status` | `tickets` | `status` | Filter list by status |
| `idx_comments_ticket_id` | `comments` | `ticket_id` | Load comments for a ticket, oldest first with `created_at` |

No full-text index. Keyword search is case-insensitive contains on `title` and `description` in JPA (see below). A `LIKE`/`LOWER` scan is enough for this assignment.

## 7. Search and status filter

List endpoint: optional `q` and `status`, combinable.

| Filter | How it hits the model |
| --- | --- |
| `status` | Equality on `tickets.status` (uses `idx_tickets_status`) |
| `q` | Case-insensitive substring on `tickets.title` **or** `tickets.description` |
| both | `AND`: row must match status and keyword |
| neither | All tickets |

Do not use PostgreSQL `ILIKE` or `tsvector` in a way that cannot run on H2. Prefer JPQL/Criteria with `LOWER(column) LIKE LOWER(concat('%', q, '%'))`, which both databases support.

Comments are not included in keyword search.

## 8. Timestamps

- Column type: `TIMESTAMP` without time zone (works the same on PostgreSQL and H2).
- Store **UTC**. The API exposes ISO-8601 UTC (`createdAt`, `updatedAt`).
- `created_at`: database default `CURRENT_TIMESTAMP` on insert; application must not overwrite it later.
- `updated_at` on tickets: set on insert; application sets it on title/description/priority, assignee, or status changes. Adding a comment does **not** require updating `tickets.updated_at` (comment has its own `created_at`).
- Comments have `created_at` only.

**Assumption:** JVM and DB session clocks are UTC in local and evaluation environments.

## 9. ID generation

- `GENERATED BY DEFAULT AS IDENTITY` on `tickets.id` and `comments.id`
- Type `BIGINT` ↔ Java `Long`
- Never send ids on create; never reuse ids in the API as client-assigned values
- H2 and PostgreSQL both support identity columns; do not use `BIGSERIAL` or sequences in a Postgres-only way

## 10. Flyway

- Versioned SQL under the backend `db/migration` folder (exact path chosen at implementation).
- One initial migration is enough, for example `V1__create_tickets_and_comments.sql`: create `tickets`, create `comments`, add CHECK constraints, add `idx_tickets_status` and `idx_comments_ticket_id`.
- Same script for PostgreSQL and H2: `BIGINT`, `VARCHAR`, `TIMESTAMP`, `IDENTITY`, `CHECK`, `FOREIGN KEY`.
- Application: `spring.flyway.enabled=true`. Do not use `ddl-auto=update` for schema changes.
- Later model changes get new versions (`V2__...`). Do not edit applied migrations.

No seed data is required unless we add it later for demos.
